# NoteFlow 九方面系统设计审查

日期：2026-11-12。代码基线：`48119903f5b26de8ea5f61e6537966a029356e76`。关联 [Issue #17](https://github.com/zczshahaha-del/NoteFlow/issues/17)。本轮交付审查与改造建议，没有修复产品代码、调整环境、迁移数据或部署。

## 结论与证据边界

现有 React / FastAPI / PostgreSQL / Redis / LangGraph / Hindsight 路线可以继续使用。账号范围仓储、正式笔记与草稿分离、版本与冲突检查、附件补偿、持久任务以及厂商适配器都有实际基础。当前适合保持一个后端应用，逐步收拢模块边界。

公开使用前的主要缺口是运维权限、旧凭证退出、统一资源预算、完整数据恢复和可选依赖故障处理。AI 资料范围、自然语言任务续接、语义质量门禁，以及大知识库工作集也尚不完整。分目录、通过常规测试或一小时运行，都不能单独证明这些边界已经成立。

证据分为：**本轮隔离复现**、**当前源码确认**、**历史运行证据**、**待验收/设计建议**。结构化记录见 [本轮检查结果](../verification/nine-aspect-review-2026-11-12.json)。

- 本轮完整后端单元发现 311 项，296 通过、15 跳过，退出 0；显式关闭真实数据库集成检查。
- 本轮实际执行正式错误中间件、健康路由、缓存/模型调用函数和备份函数；使用 ASGI、Redis/模型/数据库导出替身及临时文件，没有真实账号、邮件、模型费用或数据库写入。探针重现缺口，**不代表产品检查全部通过**。
- 2026-11-11 的真实 SMTP 登录、一小时 3 账号 10,485 次操作、PostgreSQL 并发与 Hindsight 运行结果保留为历史证据，见 [一小时报告](../verification/local-soak-2026-11-11.json) 和 [系统修复报告](../verification/system-fixes-2026-11-11.json)。
- 本轮直连回环端口 5173 / 8080 / 8888 / 9999 均连接失败，`lsof` 未发现对应监听。首次经环境代理取得的统一 502 已排除；不归因为产品缺陷，也不推断服务为什么停止。本轮未重启环境或执行新的真实服务 E2E、容量、故障重启、生产/灾备验收。

## 1. 目标与约束

**已有基础**：README 明确个人知识库与单工作台方向，有前后端、数据库和模型的配置边界；已有本机读写延迟预算和一小时轻负载实测。

**设计问题/待明确**：个人自用、小范围多用户与公开注册服务没有收敛成当前发布的明确目标；未在当前基线中找到完整的上线容量、可接受数据损失与恢复时间、月度费用及各质量目标优先级。历史低配生产方案不能直接推广到后来新增的 Hindsight；容器内存上限不能当成实际用量。

**建议修改**：补一页当前发布目标，明确用户数/同时使用量、单用户笔记与附件规模、是否允许公开注册、主机资源和月度预算。建议优先保护数据正确性与用户隔离，再明确基础笔记与可选 AI 的可用性目标。所有数字由真实使用目标确定，不能把本轮审查建议当成已批准的产品承诺。

**验收**：每个目标都能对应可执行场景和通过标准；历史 3 账号一小时只作为一个已测区间，不等于容量上限或全天负载。

## 2. 业务边界与协作（含接口、解耦）

**已有基础**：`repositories` 要求账号范围，工具层使用 `ToolContext`，模型/记忆有适配层和统一结果契约。当前目录规则有明确调用方向，架构契约测试覆盖路由 SQL、工具 ORM 依赖和仓储身份参数。

**问题 A：业务协调仍集中。** `src/store/index.tsx` 同时协调笔记保存、离线编辑、聊天、草稿、预览和检查点；Agent 路由负责规划、分支执行、事件及任务状态；笔记/草稿路由仍创建业务对象、安排索引和提交事务。3038 行 store、1619 行 Agent 路由只是定位线索，实际问题是跨职责动作和事务仍集中；不能仅按行数决定重写。沿用既有模块盘点/AI-18 的边界改进。

**修改**：前端逐步按保存、聊天、草稿、预览拆动作入口，保留必要的工作台协调；后端把“保存正文、确认草稿、应用预览”收进应用服务。路由负责协议转换，服务拥有事务与业务校验，仓储负责查询。先固定现有行为和失败用例，再逐项迁移；无需为每个模块引入独立网络服务。

**问题 B：错误契约转换丢信息（DEV-35，新确认）。** 正式中间件保留状态码、业务 code 和 request ID，却丢弃 `HTTPException.headers` 与 detail 中的冲突附加字段。隔离复现：429 无 `Retry-After`；409 的 `NOTE_VERSION_CONFLICT` 保留，但当前版本时间/hash 消失。当前前端主要显示消息，这不等于已复现正文丢失；它使接口无法完整支持既定重试与冲突协调协议。

**修改/验收**：统一错误信封支持经过白名单筛选的 `details`，保留安全响应头；客户端按稳定 code 分支。覆盖真实限流/保存路由的 429 重试提示、409 版本信息、422 字段错误、普通异常脱敏，并核对 OpenAPI 与实际响应一致。

## 3. 数据与业务正确性

**已有基础**：正式 Markdown、版本、草稿/预览、派生索引职责可辨。当前普通保存已按账号加锁并检查预期内容，AI 应用有幂等回执；附件有持久清理意图。UI-45 / UI-46 与知识库备份修复保留既有验收结论，不重复列为未修。

**问题 A：整机/整账号恢复不完整（GIT-05）。** `backup_noteflow.py` 固定读取仓库 `server/data/attachments`，忽略实际可配置根目录及生产附件卷。本轮临时文件复现：配置位置有合成附件，归档仍为空。`restore_noteflow.py` 恢复项目库及可选 Hindsight 库，未自动解包/恢复附件。知识库 JSON v2 的成功不能替代整套恢复；本轮没有读取或导出真实数据。

**修改/验收**：显式指定并校验附件来源（实际目录或容器卷），manifest 记录来源、文件数/哈希及配对备份；缺失预期目录应失败。停写后同时备份项目库、附件和 Hindsight，秘密另行安全保管。恢复到全新隔离目标，逐项核对正文、版本、附件字节、来源控制、手工修订、停用/删除规则，之后才制定切换方案。

**问题 B：图状态与业务提交分开（AI-13 等，失败窗口待验收）。** 草稿确认先调用图授权，再提交正式笔记；图和业务库不是同一事务。没有证据证明某次真实用户数据因此出错，但不能把图状态当作业务成功回执。

**修改/验收**：由业务提交记录作为完成依据，持久操作 ID 和幂等回执；图按业务结果推进，增加重试后的状态核对/修复。故障注入覆盖“图成功、SQL 失败”“SQL 成功、响应中断”“重启后重试”，确保不重复创建、不虚报完成且保留产物。

## 4. 安全与隐私

**已有基础**：HttpOnly 会话、账号范围查询、AI 身份注入、私有附件会话校验、HTML 清理及依赖锁均已存在。之前修复的 SEC-01 / 03 / 04 / 08 / 09 不再作为当前同一缺陷报告；旧依赖审计数字不等于今天重新扫描。

- **SEC-07：运维权限。** 本轮正式路由加合成诊断返回：匿名 diagnostics 为 200、匿名 metrics 为 401、普通身份 metrics 为 200。源码确认返回全局指标。公共健康检查应最小化，详细诊断/指标经独立运维身份或内网入口访问；不必为了个人笔记先建设完整团队 RBAC。
- **SEC-02：旧无 sid 凭证。** 已验证账号会拒绝旧 token，但未验证存量账号仍有兼容路径，缺少统一截止与迁移退出。应清查存量后制定期限，保留数据归属并要求邮箱证明；验证退出、重置、撤销和迁移后旧凭证失效，不在审查中批量撤销真实会话。
- **SEC-05：预算覆盖不完整。** 部分聊天路由限流；预览、草稿、RAG 评估/重建等昂贵入口缺少统一的用户/全局费用与容量控制。附件 `bytes` body 在大小检查前已完整接收。应在应用服务统一执行预算预留/结算、并发和队列上限，入口流式限制 body；避免通过换接口绕过预算。生产代理体积规则也需与应用上限一致。
- **SEC-06：匿名指标基数。** 12 个不同 404 地址新增 12 个路由键，本轮实际中间件复现。归一 unmatched 路由、限制标签基数，避免把匿名随机路径永久保存在进程内。

**验收**：匿名/普通账号/运维身份矩阵，跨账号笔记/附件/任务/记忆负面用例，旧凭证撤销、全部昂贵入口预算、超大请求提前拒绝，以及随机路径不持续增长。

来源：[身份依赖](../../server/app/deps.py)、[运维路由](../../server/app/routers/health.py)、[上传入口](../../server/app/routers/attachments.py)、[指标](../../server/app/services/observability.py)。

## 5. 可靠性与恢复

**已有基础**：索引/outbox 有持久状态、领取锁、过期领取恢复和重试；可选记忆有降级，显式记忆操作失败会反馈。API 生命周期同时启动 index/draft/outbox worker，目前是同一进程，属于现有部署取舍。

**问题 A：可选缓存可阻断主调用（DEV-36，新确认）。** Redis 在启动时能失败回退，但 `ai_cache.get/set` 在运行中不捕获断连。本轮调用正式 `complete_chat`：读取失败时模型替身调用 0 次、调用方收到 ConnectionError；写入失败时模型替身已成功返回 1 次，调用方仍收到 ConnectionError。结果是缓存故障可能被表现为 AI 失败，并诱发重复调用；未进行真实 Redis 停机或收费模型测试。

**修改/验收**：缓存读失败按未命中处理，写失败不覆盖已经成功的模型结果；记录受控故障并采用有界短超时/熔断，必要时使用有限本地缓存。鉴权、权限及配额保持各自安全策略，不能统一吞掉所有 Redis 错误。覆盖运行中读断连、写断连、恢复、并发与流式/非流式调用。

**问题 B：故障恢复证据有限。** 一小时无异常只证明该负载区间，不能证明进程被杀、DB/外部服务超时、磁盘满、重试耗尽都可恢复。部分 worker 在外部 I/O 期间持有事务或行锁，存在连接/锁占用风险，未测出具体容量上限。

**修改/验收**：先补进程中断、重放、死信与幂等的隔离演练及可观测指标；再按结果决定独立 worker 进程和缩短外部 I/O 的事务范围。独立 worker 需要领取、版本屏障和重复执行验证，不能仅移动文件即宣称隔离完成。

来源：[缓存](../../server/app/services/ai_cache.py)、[模型调用](../../server/app/services/ai.py)、[worker 生命周期](../../server/app/main.py)、[outbox worker](../../server/app/workers/outbox_worker.py)。

## 6. 性能、容量与运行成本

**已有基础**：限流、部分有界缓存、模型 token 上限、串行后台任务和本机延迟采样已存在。历史 3 个合成账号一小时未发现未处理错误，不能扩大为大库/高并发容量结论。

**问题 A：在线全量工作集（PERF-01，新确认的容量设计限制）。** `/notes` 无分页且序列化正文，前端启动请求 `listNotes(true)`；BM25 每次从 SQL 取本人全部可见 RAG 节点并分词，之后才查评分缓存。仓储替身捕获查询证实没有 SQL limit/offset；源码确认全量节点路径。没有执行大规模压测，不声称当前已卡顿或已发生 OOM。

**修改/验收**：目录使用元数据/摘要分页，正文按需加载；回收站与版本单独分页。BM25 采用持久或按索引版本复用的分词/检索结构，避免每请求全量加载/分词；保留账号、删除和来源版本过滤。用按目标确定的库大小阶梯测启动、搜索、正文打开、峰值 RSS 和后台积压。

**问题 B：费用与连接预算。** 当前费用是进程内估算，未形成持久的用户账本与硬预算；价格默认可为 0，也不等于外部服务免费。SQLAlchemy 每进程池配置 10+90，尚未结合数据库连接上限、worker 和小主机容量统一规划。

**修改/验收**：区分交互、生成、索引、记忆等成本，关联 run/user/model/usage，允许价格缺失时显示未知；先做配额再做对账。连接池按总进程数和数据库容量规划，测等待与超时；不要直接调大连接数或只以平均延迟验收。沿用 SEC-05。

## 9. AI 行为与质量

- **AI-17：读取范围不是硬边界。** `contextScope` 仅出现在后端 schema。正式 `_planner_messages` 对 auto / selection / current_note / knowledge_base 四种范围产生完全相同消息，本轮合成复现；读取端未把它作为权限/范围上限。这是同账号资料使用范围问题，不据此声称存在跨账号泄露。应定义枚举化 `ContextPolicy`：用户选择限定可读集合，后台身份校验后，Planner 只能在其子集中选择。覆盖移除引用、选区、全库、未保存正文和重试。
- **AI-13：自然语言续接与执行协议不完整。** 正式 PrimaryIntent 及兼容映射无法产生部分遗留续接/历史召回分支，映射仍固定 `continue_working_task=False`；活动任务没有统一进入正式任务关系协议。LangGraph 澄清续接、按钮或业务 API 能用不等于任意自然语言“继续上一项”都可达。应由服务端加载本人会话任务快照，规划明确任务目标和动作，再路由到当前执行器；验收同任务继续、新任务切换、澄清、取消和刷新，避免仅增加关键词分支。
- **AI-14：语义质量证据不足。** 旧管理函数入口已经在 DEV-33 修复；当前离线 manage 验证固定 PlannerOutput，`--live-planner` 可验证自然语言；extract 仍使用规则函数，不能代替正式智能提取与长期事实质量。现有 12 条基线和两项历史真实模型调用的范围需保留。应扩充中文任务、资料注入、引用依据、纠正/忘记/冲突/近似重复数据集，分开报告协议、真实语义、检索、业务结果和成本，保留人工复核与模型/提示参数。
- **AI-16 / AI-15：同一任务版本与证据关联。** 模板已有独立版本和热激活；跨重启续写仍可能使用新版本，运行记录缺少完整的模型/模板/digest/检索快照绑定。应在任务创建时固定运行配置，后续章节及恢复沿用该版本，显式升级才切换。追踪依据、工具入参摘要及已确认业务回执，不要求保存模型隐含思考内容。
